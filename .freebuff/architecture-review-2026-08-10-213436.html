Problem

Five endpoints inline their business logic inside HTTP plumbing, and the same 200/500 JSON framing is hand-rolled four times. The budgeted latency benchmark lives inside the server file.

Solution

Each endpoint becomes a function returning (status, payload); do_GET becomes a dispatch table plus one framing helper; the benchmark moves to tools/.

Wins

  • HTTP framing written once, not four times
  • endpoint tests stop faking HTTP requests
  • error semantics local to one helper
  • serve_web_app sheds ~100 lines

2 · Version and project the feed at the seam

Strong in-process

app/src/pipeline/phase3_simulation_rank.py (feed writer) · app/src/server/serve_web_app.py · app/web/js/app.js (1556 lines)

Before — the page reads the whole scan

FEED_URL → fetch whole JSON

phase3_simulated_targets.json

summary wallet A (full record) wallet B (full record) … × 100+

breakdown · labels · radar · activity · metrics · bankroll · cap_sweep · skips · misses — every wallet, for a grid that reads ~12 fields per row

JS: `row.cap_sweep || []` `|| 0` `|| "Not measured"`

unversioned shape → every deep read defended with fallbacks; an old cached scan silently lacks new keys

After — one declared shape, detail on demand

/api/feed → summary + row projection

grid payload (small)

feed_version: 3 12 fields × rows full record per wallet on demand

the version tells the page which keys exist — old feeds degrade visibly, not silently

Problem

The grid fetches every wallet's full record, and the browser guards every deep read with fallbacks because the feed shape is unversioned — the serving contract is implicit and guessable.

Solution

Publish a feed_version; serve the grid from a projection endpoint; the modal lazy-loads one wallet's full record. The page stops guessing which keys exist.

Wins

  • initial paint reads a slice, not the whole scan
  • one declared feed shape, versioned
  • old cached feeds degrade visibly, not silently
  • modal detail fetched only when opened

3 · Table-driven triage engine

Strong in-process

app/src/screener/score_wallets.py (573 lines) · tests/test_score_wallets.py (413 lines)

Before — interface as wide as the implementation

interface: score(metrics, profile)

10 hand-written interpolation blocks + 8 hand-written gates
spec & code can drift — a reweight edits both
labels & radar names rebuilt per call

After — small interface, deep implementation

interface: score(metrics, profile) — unchanged

SCORING_SPEC entries carry curve descriptors
one `_score_parameter` helper evaluates them all
gates read from one predicate table

Problem

Ten parameters are hand-evaluated in ten near-identical blocks while SCORING_SPEC already declares them as data. Reweights are this repo's most frequent change (#9, #16, #23) — and each one means editing copy-paste blocks and the spec and regenerating docs.

Solution

Curve descriptors (key · points · zero_at · full_at) live in the spec; one helper evaluates every parameter; gates come from a small predicate table. The interface stays score(metrics, profile).

Wins

  • a reweight is one table edit, not three places
  • spec and code cannot drift apart
  • one helper is the test surface for N parameters
  • ~150 lines of repetition deleted

"what a sweep result means" is split: the sweep produces the dict, phase3 classifies endpoint-failure vs measured rejection, stamps tiers, extracts misses, shapes the feed — and the web endpoint reaches into phase3 for the cap backtest.

After — one seam, verdict semantics local

flowchart LR
  P3["phase3: loop + degrade + feed"] --> V["verdict_for_wallet(wallet, profile)"]
  WEB["serve_web_app cap_backtest"] --> V

scan, endpoint and tests cross one interface; ADR 0007's endpoint-failure classification is written and tested once.

Keeps ADR 0002's split — triage grades stay leaderboard-fed and work when the endpoint is down; this module is the verdict side only.

Problem

phase3 is three responsibilities at once, and the interpretation knowledge leaks across its seams to the sweep (producer), the parser, the tier constants, and the web endpoint — so changing "what a verdict means" touches several modules.

Solution

A deep module behind verdict_for_wallet(wallet, profile, fetcher, cache_dir) → verdict owning the sweep call, failure classification, tier stamping and verdict-side metrics. phase3 keeps the loop, degradation and feed shape.

Wins

  • verdict semantics local to one module
  • scan, endpoint and tests cross one interface
  • ADR 0007 classification tested once
  • phase3 sheds ~120 lines

5 · One paths module

Speculative in-process

every module under app/src/** — seven copies of the same bootstrap ritual

Before — the layout ritual, seven times

SCRIPT_DIR = dirname(abspath(__file__))
SRC_DIR = abspath(join(SCRIPT_DIR, "..", ".."))
if SRC_DIR not in sys.path: sys.path.insert(0, SRC_DIR)

repeated in phase1, phase2, phase3, run_mock_client, slippage_sweep, serve_web_app, leaderboard_adapter …

the dataset file inventory (phase1/2/3 outputs) is stated in three separate modules plus the reset list

After — the layout is known in one place

paths.py

SRC_DIR · DATA_DIR · DATASETS = {phase1, phase2, phase3}

WALLETS_FEED · TARGETS_FEED · VERDICT_FEED

every module imports the names; reset_data_cache reads the same inventory it deletes

Problem

The source/data layout is re-derived in every module, and the dataset file inventory is duplicated across the phases and the reset module — a rename or a move touches N copies of the same lines.

Solution

One paths.py exposing the directories and the dataset file names; modules import instead of bootstrap.

Wins

  • layout and inventory known once
  • dataset names stated in exactly one place
  • deletes the ritual from seven modules

Top recommendation

Tackle 1 · Endpoints behind the router first

It is the seam this review was asked about — the serving layer — and it is the smallest, highest-certainty win: the router is demonstrably shallow, the seam is already proven testable in-process, and deepening it unblocks candidate 2's projection endpoint. Candidate 3 is the strongest pure-deepening in the repo and worth pairing with it, since a reweight is the change this codebase makes most often.
